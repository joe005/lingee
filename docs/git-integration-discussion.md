# Git 研发与代码集成设计讨论稿

> 状态：修订待评审。本文包含对抗性审查后的设计建议，不代表当前原型已实现；待确认后再同步模块需求与页面。本文中“一期”指真实集成闭环的范围，原型演示须另行标明模拟状态。

## 1. 目标与边界

一个开发空间关联一个 Git 仓库和基准分支，一个研发任务使用独立任务分支。任务成果经验证、评审后，合入该空间配置的基准分支。

- 合并入口在 Build，Manage 保持管理视图，不放待合并清单。
- 测试人员负责测试结论，开发负责人负责代码集成与合并决策。
- 新任务的合并目标默认取空间配置，可能是 main、master、develop 或其他分支，界面不可写死 main。任务开始时保存仓库标识和目标分支快照，创建请求沿用该快照；后续空间配置变化不自动改变进行中任务和历史请求的目标。
- 任务阶段完成、测试通过、代码已合并、交付条件满足是不同事实，分别记录。只有实际合并与交付条件均得到确认，研发任务才完成。
- Git 平台提供实际分支、请求、检查、审批和合并事实；Build 维护集成协作、证据关联和待办；Manage 保存任务整体状态与管理统计。

当前原型已经展示任务分支与基准分支，但直接按任务「已完成」推导「已合并」，没有真实 Git 操作与合并请求闭环。本方案需要替换这一推导方式。

## 2. 入口与页面

### Build → 协作开发 → 代码集成

增加与「任务」平级的「代码集成」页签。页签徽标统计待本人处理的合并请求，页面支持按空间切换仓库，默认显示「待我处理」。

列表提供「待我处理、全部进行中、已合并、已关闭」视图，并可按集成状态筛选。待我处理包含需要本人解决冲突、评审、复测、确认合并或处理异常的请求；需要多方处理时分别生成对应待办，同一请求的徽标计数按请求去重。「已合并」仍包含交付条件未满足的异常请求，并明确提示异常。

| 列表信息 | 内容 |
| --- | --- |
| 关联任务 | 编号、名称、所属空间 |
| 分支 | 任务分支 → 基准分支 |
| 处理人 | 当前待办负责人；并行待办显示多人，另展示代码集成负责人 |
| 集成状态 | 待检查、有冲突、待验证、待评审、可合并、合并中、交付异常等 |
| 质量信息 | 任务测试结论、当前版本自动检查与复测结果 |

点击条目打开集成详情，集中展示变更摘要、来源与目标分支、版本标识、检查与复测证据、待办和处理记录。文件差异、逐行代码评审与冲突编辑一期跳转代码平台或本地工具，详情提供对应 MR/PR 链接。

根据状态提供「检查最新状态」「处理冲突」「请求复测」「查看合并请求」「合并到〈目标分支〉」等操作。界面同时说明不能合并的具体原因，并展示最后同步时间；同步失败或结果不明时停止提供合并动作，不把旧状态当成最新结果。

### 任务详情中的关联入口

任务详情保留「代码集成」卡片，展示来源分支、目标分支、当前状态、当前处理人及关联 MR/PR；点击进入同一份集成详情，不另建一套流程。

测试人员完成最后节点时，操作仍为「测试通过」。MR/PR 可在首次推送后提前创建为草稿；测试通过后更新其就绪状态，进入集成流程并交给代码集成负责人，不要求测试人员处理 Git。尚未创建请求或授权不足时保留测试结论，明确展示待创建或待授权。

## 3. 角色与权限

| 角色 | 职责 |
| --- | --- |
| 任务开发人员 | 提交与推送任务分支，修复检查问题，解决冲突 |
| 测试人员 | 验证任务功能，按复测待办验证受影响范围 |
| 代码评审人 | 检查当前版本差异和冲突解决结果，给出评审结论 |
| 开发负责人／合并人 | 接收待合并请求，协调处理，确认合入基准分支 |
| AI 智能体 | 在获授权的执行环境中执行检查、生成影响分析与复测建议；辅助解决冲突，一期由开发人员审查并提交结果 |

每个开发空间指定默认代码集成负责人，创建合并请求时可在有权限的人员中调整；这是独立职责，不默认等于最后阶段测试人员或空间负责人。

Build 的处理人分配用于协作路由，实际合并权限、必要审批和保护分支规则以代码平台为准。AI 无法判断业务意图时，交给开发人员确认，不能静默选择一方覆盖。

集成负责人、评审人和复测人员即使未参与原执行阶段，也须能读取完成本次职责所需的任务上下文、差异和验证证据。授权由 Manage 校验同一租户、空间成员身份和具体职责，限制到关联任务与证据；分配集成职责不授予空间管理权限或 Git 写权限。接收待办前检查访问条件，不向无权处理的人发出不可操作的待办；成员离开或权限撤销时暂停其动作并通知负责人重新分配。

### 执行身份与授权

| 执行方 | 使用身份与职责 |
| --- | --- |
| 本机客户端 | 使用开发人员保存在本机系统凭据库的账号拉取、推送，打开本地任务工作区；本机离线时不承担后台同步 |
| 集成后端 | 使用空间管理员单独配置、限定仓库范围的集成凭据，创建或关联请求、读取状态、接收平台事件并定期对账；凭据存入服务端密钥存储，不读取或上传本机钥匙串令牌 |
| CI 与测试环境 | 使用已有流水线执行身份生成检查、构建和部署证据；检查任务不获得合并凭据 |
| 合并人 | 一期默认在代码平台使用本人账号确认合并；Build 内合并仅在已接通本人平台授权、能核验实际权限并保留操作归属时开放 |

设置页分别显示“本机 Git 可用”和“集成服务可用”，单独检测仓库读取、推送、请求读写、检查回写及合并能力；某项成功不推导其他项有权限。集成服务未配置或凭据失效时显示待授权，保留人工创建并关联请求的入口，不宣称已自动创建或已检查。测试人员通过无需持有 Git 凭据。

## 4. 主流程

1. **开始任务**：确认代码交付方式，保存仓库和目标分支快照，从该分支创建任务分支，例如 feature/t1001601，在独立任务工作区开发。
2. **首次推送**：集成服务创建或关联草稿 MR/PR，使依赖请求触发的 CI 可以提前运行。关联时校验仓库、来源、目标和所属任务，不能只凭 URL 认领请求。创建失败不阻断已有开发，但在任务卡片中持续提示。
3. **开发与测试**：阶段按执行计划推进，测试前核对构建产物和环境实际版本。首次测试可以基于任务分支，之后仍需验证其与最新目标分支组合。
4. **测试通过**：最后测试节点完成后，代码任务主状态进入「待交付」，显示「测试已通过 · 待合并」；集成服务将请求更新为就绪并分配给代码集成负责人。缺少请求或权限时保留测试结论，生成明确的补办待办。
5. **集成检查**：读取任务分支、目标分支、CI 和审批最新状态，生成或获取集成候选版本，并对该候选运行已有 CI。冲突交由开发侧处理，检查失败先修复，人工复测通过或获准免测后再判断可合并。
6. **确认合并**：满足第 6 节的门禁及平台保护要求后，由有权限的人确认。平台接受请求或进入队列只表示「合并中」，实际合并结果须继续回查。
7. **同步交付**：核对实际合并的请求、仓库、目标和版本与有效证据的对应关系。条件齐全后由 Build 向 Manage 申请完成，Manage 统一校验并写入任务完成；条件缺失则记录真实已合并事实，进入交付异常。

任务开始时区分“代码交付”和“非代码交付”，不能因当前差异为空自动判定无须合并。非代码任务沿用现有完成流程；代码任务最终无须代码变更时，由任务负责人说明理由，经代码集成负责人确认后转为非代码交付，保留记录。

一期支持一个任务对应一个仓库、一个必要合并请求；关闭后重提保留历次请求关系，同一时刻仅一个为当前必要请求。多请求或跨仓库任务明确提示超出一期范围，不按部分合并判定完成。

## 5. 状态口径

任务主状态、平台请求生命周期和集成门禁分别保存。平台请求统一展示为草稿、打开、已合并、已关闭，保留平台原始状态与草稿标记用于核对；集成门禁可同时存在多项阻塞，界面展示主要原因和全部待办，不以单一状态覆盖其他未完成条件。同步健康状况单独显示。

| 任务主状态／进展 | 集成情况 | 用户看到的文案示例 |
| --- | --- | --- |
| 开发或测试中 | 开发中 | 测试中 · feature/t1001601 |
| 待交付 | 待创建／待授权 | 测试已通过 · 合并请求待创建 |
| 待交付 | 待检查／待评审 | 测试已通过 · 待合并 |
| 待交付 | 有冲突 | 待合并 · 冲突待张工处理 |
| 待交付 | 待验证 | 代码已更新 · 等待复测 |
| 待交付 | 可合并 | 可合并到〈目标分支〉 |
| 待交付 | 合并中／结果待确认 | 正在确认合并结果 |
| 待交付 | 已合并，交付条件缺失 | 已合并 · 交付异常待处理 |
| 待交付 | 已合并，完成状态回写失败 | 已合并 · 完成状态同步中 |
| 已完成 | 已合并且交付条件满足 | 已合并到〈实际目标分支〉 |
| 待交付 | 已关闭且未合并 | 合并请求已关闭 · 待决定重提或取消 |
| 已取消 | 后续发现实际已合并 | 已取消 · 检测到合并，需人工处置 |

「待合并」是任务主状态「待交付」下的显示摘要。修复或复测失败需要重做阶段时，任务回到执行中并保留既有记录；此前“测试通过”仅作为历史证据，不继续显示为当前版本结论。请求关闭不等于任务完成，由负责人决定重提或取消。

### 与现有任务流程的衔接

- Manage 新增并持有「待交付」主状态，Build 回写阶段完成与集成事实。涉及代码交付时，取消现有“最后阶段完成即任务完成”的直接出口，包括关闭人工评审后的自动完成、人工验收、拖拽或接口直接改为完成等路径，统一经过完成条件校验。
- 代码任务完成条件为：未取消、所有必要阶段完成、当前必要请求在约定仓库与目标上实际合并、对应版本的必要检查和审批有效、必要人工复测通过或按规则获准免测、无待处理交付异常。免测不能替代必需的自动检查和平台审批。
- Manage 的项目与里程碑完成统计仅计算整体已完成的任务，待交付仍为未完成。Build 现有“我的阶段已做完”归类可以保留，但卡片须展示任务实际状态；新的集成待办纳入“待我处理”，避免只剩阶段参与人可见。
- 任务取消或删除后停止新建请求与合并动作，保留集成关联和审计记录；迟到事件不自动恢复任务或标记完成，已发出的合并若无法撤销则交给负责人处置。任务删除不连带删除远端分支或 MR/PR。
- 已有完成任务不得按 `done` 自动补造“已合并”事实。迁移时显示“历史完成 · 合并状态未核实”，有平台证据后再补齐；不因缺少新证据自动重开所有历史任务。

## 6. 冲突处理与复测

### 冲突在开发侧解决

代码集成详情展示冲突提示和处理人，一期提供「在代码平台处理」与「在本地打开」。开发人员可在现有开发工具中让 AI 辅助，审查结果后提交并推送回任务分支，更新原 MR/PR，保留处理前后版本及解决说明。内置 AI 自动解决、提交和推送后置。

解决冲突不等于检查通过，也不能直接把任务标记为已完成。

### 解决后是否再测试

原则是：测试证据只对已验证的代码版本有效。冲突解决或其他代码更新后，重新运行对应检查，并按影响范围决定人工复测。

| 变更情况 | 必要验证 | 人工复测 |
| --- | --- | --- |
| 无冲突，目标分支已更新 | 验证最新任务分支与目标分支组合，运行构建及适用的自动化测试 | 按影响范围决定 |
| 冲突解决修改可执行代码 | 重新构建、运行相关自动化测试及集成检查 | 开发人员说明影响范围，涉及功能行为时安排针对性复测 |
| 涉及业务逻辑、接口、权限、数据结构 | 增加相关回归、兼容性和数据验证 | 必须针对受影响功能复测 |
| 仅文档、注释等变化 | 做与变更相适应的检查 | 可免功能复测，记录理由 |

AI 可以建议复测范围，人工免测由有权限的代码集成负责人确认，并保留对应版本、变更范围和理由；涉及业务逻辑、接口、权限或数据结构时不能按此免测。不能仅以「Git 没有冲突」或「任务以前测试通过」作为免测理由。

复测待办包含关联任务、变更摘要、影响范围、重点场景、测试环境与代码版本。测试人员从任务待办进入即可，无需操作分支；复测失败回到开发侧修复，保留原始测试和失败记录。

### 确认测试对象

测试交接至少提供：不可变的构建产物标识、其来源提交或集成候选版本、构建记录、部署记录、测试地址与环境实际运行版本。CI 或部署系统提供这些记录；测试人员填写一个分支名不能替代实际版本核验。

开始测试和确认通过时均核对产物与环境版本；测试期间若环境部署变化，本次结论不得直接通过，需确认是否重新测试。无法获取可靠版本的环境展示“版本未核实”，补齐证据后才能提交通过结论。共享环境需提供测试期间的部署记录或占用保护，不能因已有独立 Git 工作区就认为环境已隔离。非运行类交付物按不可变文件或产物标识核对，不要求部署环境。

一期复用已有 CI、部署和测试环境，接通版本证据；环境不可用时停在待验证，不自动视为通过，也不在本方案中自建一套部署系统。

### 防止旧结果误放行

- 每次集成验证同时记录仓库标识、来源分支及提交 SHA、目标分支及提交 SHA、集成候选提交或可复现的代码树标识、合并策略、检查配置版本及流水线记录。测试证据还关联实际构建产物与环境，审批保留审批人、版本和结论。
- 冲突解决或其他来源代码更新后，原候选失效。目标分支更新或合并策略变化也须重新生成候选、执行适用检查；此前证据保留为历史。人工复测是否需要重做按影响范围重新判定，不自动沿用旧免测结论。
- 任务分支上的测试可以保留为该提交的证据，但不能替代集成候选验证。合并后保存实际合并提交与候选的对应记录；squash 或 rebase 导致 SHA 不同，须通过平台记录和代码树等证据确认对应关系，不能只比较提交 SHA，也不能只看请求已合并。

### 门禁在代码平台执行

空间启用集成前，管理员确认平台实际版本、仓库保护规则和已有 CI 能力。必要 CI、审批以及 Lingee 的阶段／人工复测条件均需落实为平台可强制的检查或等效规则；集成服务维护自身检查结果，并确保新候选尚未验证时为未通过。检查写入权限须限制到可信执行身份，开发人员不能通过自报成功替代证据。

“确认合并前再读一次状态”和“Lingee 内按顺序合并”都不能独立消除外部并发。平台须具备并启用以下一种可验证机制：原生合并队列／合并列车对最新目标组合执行检查；或要求来源更新到最新目标、对更新后的组合执行检查，并由平台在合并时强制拦截过期组合。源提交校验只是其中一项，不能代替目标组合保护。采用哪种机制须在一期平台验证中确认，不由 Lingee 自研队列兜底。

能力、版本或保护配置不足的仓库仅开放关联、读取与协作提示，不显示“受门禁保护的可合并”，也不开放 Build 内合并。跳转平台不会豁免 Lingee 交付条件。平台管理员绕过保护或外部提前合并时，系统如实记录已合并事实，检查缺失条件并进入「交付异常」；由负责人安排实际合并产物的补充验证或创建回退任务，不能把事后验证伪装为合并前通过。补救记录齐全并获确认后才允许完成原任务。

### 仓库与目标变更

空间配置修改只影响新开始的任务。进行中任务若确需更换仓库或目标分支，由有空间配置权限的人显式发起，并由代码集成负责人确认；保存变更原因与前后快照，失效旧候选和门禁，更新或重建请求后重新验证。请求在平台被直接改投目标时也先暂停集成，完成同样的确认，不自动接受新目标。

已合并请求的历史仓库、目标与证据保持原样。源／目标分支被删除、仓库不可访问或迁移未确认时进入阻塞，不能自动改用空间最新配置、同名分支或默认分支继续合并。

## 7. 一期范围

优先接通「首次推送关联草稿请求 → 测试通过后待交付 → 问题处理 → 候选验证与评审 → 人工确认合并 → 对账后完成」闭环。

- 建议先接金蝶 GitLab，以实际部署版本和授权能力验证为准；GitHub、Gitee 及其他实例后续按同一契约适配，不在一期同时铺开。
- 支持一个任务关联一个当前必要请求、草稿创建、待办路由、阶段与交付状态分离，以及后台回查。集成凭据按空间授权，个人本机 Git 认证沿用现有设计。
- 复用已有 CI 与测试环境，提供候选版本证据、复测待办和冲突处理链接。缺少运行环境或平台能力时明确阻塞，不声称完成验证。
- 一期默认跳转平台由本人确认合并；Build 内合并作为通过授权与门禁验证后的增强能力。两条入口使用相同交付条件。
- 暂不实现内嵌完整代码审查、AI 自动提交冲突结果、自研合并队列、部署编排、版本发布、跨仓库原子交付。

合并后的发布和发布验收属于后续交付流程；本方案中的任务完成表示代码已按要求合入约定目标且本次交付证据齐全，不表示已经发布上线。空间若另有合并后回归要求，应配置为完成条件，不可默认为已经执行。

## 8. 同步、重试与异常恢复

Build 保存稳定的集成请求 ID，以租户、空间、任务、仓库标识关联平台请求 ID，并保留历次请求记录。创建超时先查找已创建请求，核对来源与目标后关联；不存在时才重试。同一任务的创建／更新操作需幂等，避免重复请求和重复待办。

平台事件用于及时刷新，事件来源需认证、投递需去重；事件到达后读取平台最新事实，不直接用迟到事件覆盖新状态。后台周期对账覆盖漏事件，列表进入、手动刷新和合并前补充回查。权限失效、网络中断或限流时保存上次事实和同步异常，按退避策略重试，并向集成负责人展示原因。

| 异常 | 系统处理 |
| --- | --- |
| 创建／合并调用超时 | 显示结果待确认，先回查实际结果，禁止盲目重复发起 |
| 平台接受合并或加入队列 | 保持合并中，直至确认已合并、失败或退出队列 |
| 源或目标在验证后变化 | 候选与相关门禁失效，重新检查和分配受影响待办 |
| 外部合并且条件缺失 | 保留已合并事实，标记交付异常，发起补救待办 |
| Git 已合并、Manage 回写失败 | 重试同一次完成申请，保持待交付并显示同步中，不再次合并 |
| 取消／删除后收到合并结果 | 保留任务终态与历史，通知负责人处理，不自动恢复 |
| 请求关闭或被替换 | 撤销失效待办；新请求重新校验并保留前后关系 |

Manage 通过版本号或等效并发控制接收完成申请，拒绝覆盖较新的取消、删除或重开动作；重复申请返回已有结果。合并事实已确认后，不因后续请求被清理或读取失败改写为未合并；已完成任务遭到后续回退时新增风险记录与修复／回退任务，保留原交付历史。

## 9. 验收场景

| 场景 | 必须达到的结果 |
| --- | --- |
| 无 Git 凭据的测试人员确认通过，开发人员离线 | 后台使用独立集成授权推进；未授权则明确待授权，不丢测试结论 |
| 首次推送触发仅针对 MR 的 CI | 测试结束前已有草稿请求并能看到实际 CI 结果 |
| 复测未完成却在平台合并 | 正常保护应阻止；被管理员绕过时记录已合并和交付异常，任务不自动完成 |
| 验证后另一请求先合入目标，或来源追加提交 | 平台阻止过期组合合并，或原生队列重新验证；旧证据不放行新组合 |
| 复测待办为 S2，环境实际为 S1，或测试途中部署改变 | 不允许直接确认通过，展示版本差异并要求重新验证 |
| 创建请求成功但响应丢失；事件重复或乱序 | 找回同一请求，不重复建请求／待办，最终状态与平台一致 |
| 合并已成功但任务完成回写失败 | 显示同步异常，恢复后只完成一次，不再次发起合并 |
| 空间从 develop 改为 release | 旧任务与历史目标不变；显式改投后重新生成候选并验证 |
| 集成负责人未参与原任务阶段 | 能访问职责所需证据；无关任务和 Git 写权限不会随之开放 |
| 所有阶段完成、请求关闭，或任务已取消 | 均不因阶段结束或迟到事件误判交付完成 |
| 存量任务为已完成但没有 Git 合并记录 | 展示历史完成且合并未核实，不生成虚假合并证据 |

## 10. 竞品参考与适用边界

| 参考 | 官方资料中的做法 | 本方案借鉴 |
| --- | --- | --- |
| Multica GitHub 集成 | 任务侧栏关联 PR，展示 CI 与可合并状态，链接到 GitHub | 任务详情保留合并卡片，以真实平台状态为依据 |
| Multica 官方教程 | 用户确认后要求开发智能体合并，示例在合并后的 main 上重跑检查 | 开发侧负责合并，交付与检查记录可追溯 |
| Multica 本地 Worktree | 每个任务使用分支；运行详情提供分支，用户自行合并；本机修改与智能体修改冲突时由智能体处理 | 独立工作区及冲突处理，不把本地分支产出等同于已合并 |
| Qoder Worktree | 在独立工作区开发与验证，审查后将成果带回本地 | 隔离执行、审查后接收成果 |
| QoderWake 研发 Demo | 开发、自测与 PR 评审后人工合入迭代分支，再由 Tester 验收；代码更新后重新评审 | 角色分工、版本绑定证据和独立 CI 门禁 |

## 11. 评审重点与落地前置条件

1. 产品口径：采用 Build「代码集成」页签与任务关联入口，集成负责人按空间默认、逐请求调整；确认「待交付」主状态及 Manage 完成统计，并同步任务、项目协作和 Manage 对接需求。
2. 平台验证：以金蝶 GitLab 为一期建议，验证实际版本、候选流水线、审批、受保护分支及并发合并约束；明确能提供门禁保证的仓库范围，不以公共文档推定内部实例能力。
3. 授权接入：确认集成后端的仓库范围、请求读写与检查回写权限、密钥存储和网络可达性；Build 内合并另验本人授权，默认保留平台合并入口。
4. 证据接入：确认 CI、构建产物、部署环境的版本核验来源；上述验收场景通过后再启用真实闭环。原型演示可以模拟，但必须标识模拟结果，不携带真实凭据。

平台能力核对参考：[GitLab 合并请求 API](https://docs.gitlab.com/api/merge_requests/)、[GitLab 合并列车](https://docs.gitlab.com/ci/pipelines/merge_trains/)、[GitHub 合并 API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)、[GitHub 合并队列](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)。这些资料用于接口验证，实际可用能力以接入实例为准。
