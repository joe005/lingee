# 专家团需求说明书

| | |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-09-07 |
| 作者 | wuhc |
| 原型 | 本仓库 `main` 分支 `66cd005`，`npm run dev` 后进入侧栏「专家」 |
| 参考实现 | `lingee-build/packages/opencode` |

把「谁来干这件事」变成用户可见、可配置的对象：单个专家、由专家组成的专家团，以及会话里对它们的选择与自动匹配。本文交付给开发实现，包含数据模型、与 `expert_team_dispatch` 的对接规则、需平台配合的缺口，以及测试要点。

---

## 1. 背景与范围

底层的多智能体编排能力（`expert_team_dispatch`、8 个内置专家、`software-company` 专家团）已经在 `packages/opencode` 里跑通，但对用户是不可见的——用户只能提一句需求，看不到是谁在干活，也无法指定。本次要补的是这一层的产品化。

**范围内**

- 专家库页面：专家团 / 专家两个页签，浏览、搜索、新建
- 专家详情与「召唤」：选中该专家并带出触发词开启会话
- 创建专家：手填表单，或一句话交给 `expert-manager` 在对话里建
- 专家团配置：成员、组长、常见触发词；运行流程由成员推导后只读展示
- 会话输入框的专家选择器；未选择时按任务描述自动匹配

**范围外**

- 专家市场（他人发布 / 下载 / 评分）——本期只有内置 + 我创建的
- 多人共享同一个 Run（`participants` 多用户协作）
- 专家团的运行态可视化（任务卡、Attempt 进度、Review 交互）——另立需求
- 专家的知识库、工具策略、输出 Schema 的可视化编辑

## 2. 概念对齐

先统一叫法。左列是给用户看的词，中列是代码里的实体，一一对应，UI 文案不得自造第三种说法。

| 用户侧 | 实现侧 | 说明 |
| --- | --- | --- |
| 专家 | `expert-definition.json`，`expertType: "agent"` | 一个有职业身份、能力项、工作方式与约束的智能体。内置 8 个。 |
| 专家团 | `expert-team.json`，`expertType: "team"` | 一组专家 + 一位组长（`leadAgent`）+ 编排策略（`orchestrationPolicyRef`）。内置 1 个 `software-company`。 |
| 常见触发词 | `quickPrompts` | 用户平时会怎么开口找他做事。**不是斜杠命令**，是整句自然语言。 |
| 可承担的工作 | `allowedWorkModes` | 七选多：`analysis / design / implementation / integration / review / verification / recovery`。决定他在团里能领哪类任务。 |
| 能力项 | `competencies` | `{ competencyId, level }`，level 四档 `awareness / practitioner / advanced / principal`。 |
| 运行流程 | Task DAG | 由成员推导出的任务图，节点 kind 取 `analyze / design / implement / test / integrate / review`。 |
| 召唤 | 选中 + 预填 `quickPrompts[0]` | 一步动作：选中该对象、跳到新会话、把第一条触发词填进输入框。 |

## 3. 信息架构

会话和专家库是两条线，唯一的交汇点是输入框左侧的专家选择器。专家库只负责「定义谁」，不负责「开会话」——除了「召唤」这一个明确的跳转动作。

```
侧栏「专家」 → 专家库（专家团 / 专家 两个页签）

专家卡片 → 详情弹窗
        ↘ 悬停「召唤」 → 新会话（已选中 + 已填触发词）

新会话输入框 → 专家选择器 → 选专家团 / 选单个专家 / 不选
```

侧栏「专家」入口放在开发类板块（应用开发 / 技能开发 / 智能体开发）之后。

## 4. 功能需求

状态标记：**[原型已实现]** 指原型里已有可运行的交互，实现时以原型为准；**[待实现]** 指原型未覆盖、本期要做；**[需平台配合]** 指前端做不完，依赖 `packages/opencode` 改动。

### 4.1 专家库

#### FR-01 两个页签，各自带数量 [原型已实现]

页面头部为「专家」标题 + 右上新建按钮；工具栏为「专家团 *n*」「专家 *n*」两个页签 + 搜索框。数量为该页签当前全部条目数（内置 + 我创建的），不随搜索变化。

右上新建按钮的文案与动作跟随当前页签：专家团页签为「新建专家团」，专家页签为「创建专家」。

#### FR-02 卡片与快速召唤 [原型已实现]

专家卡：头像、名称、职称 · 来源、简介、标签（最多 3 个）。专家团卡：成员头像叠图（最多 4 个）、名称、来源 · 成员数、简介、成员职称（最多 3 个）。

内置条目标「内置」，我创建的标「我创建的」，只读专家标「只读」。

鼠标悬停时卡片右上出现「召唤」按钮：点击**不打开弹窗**，直接执行召唤（见 FR-04）。触摸设备上常驻显示。点卡片其余区域打开详情 / 配置弹窗。

#### FR-03 搜索与空态 [原型已实现]

搜索命中范围：专家匹配名称 / 职称 / 简介 / 标签；专家团匹配名称 / 简介 / 成员名称。无关键词时列表末尾追加一张虚线「创建」卡片；有关键词且无结果时显示「没有匹配的结果」，不显示创建卡片。

第一阶段不分页、不折叠，全部平铺。

### 4.2 专家详情与召唤

#### FR-04 召唤是一个三合一动作 [原型已实现]

无论从卡片悬停按钮、详情底部「召唤专家」、还是专家团弹窗底部「召唤专家团」触发，行为一致：

1. 把该专家 / 专家团设为当前会话的选中对象
2. 切到新会话页
3. 把 `quickPrompts[0]` 填进输入框，光标置于末尾，发送按钮进入可用态

点击详情里的**某一条具体触发词**时同样执行这三步，只是填入的是被点的那条。此前的实现只填文本不选中对象，是缺陷。

若该对象没有配置任何触发词，则只做前两步，输入框保持为空。

#### FR-05 详情弹窗内容 [原型已实现]

自上而下：头像 + 名称（+ 只读 / 我创建的标记）+ 职称 · 来源；简介；常见触发词（可点，见 FR-04）；能力项；可承担的工作；专属产物；工作方式（`workflow.steps`）；行为约束（`constraints`）。空的分区整段不渲染。

底部：内置专家只有「召唤专家」；我创建的额外有「删除该专家」（左置）与「编辑」。

弹窗高度受限时由内容区自身滚动，页脚始终贴底。

### 4.3 创建专家

#### FR-06 两条路径并存 [原型已实现]

**路径一 · 手填表单。** 弹窗分两个页签：

- **专家**：名称`必填`、职称`必填`、简介、标签、头像、可承担的工作`必填`
- **触发词与工作方式**：常见触发词（可增删多条）、能力项、工作方式、行为约束

校验不通过时自动切回出问题的那个页签并聚焦对应字段。「可承担的工作」不能为空——为空则该专家在任何专家团里都领不到任务。

**路径二 · 一句话。** 表单顶部常驻入口「不想填表单？一句话交给 expert-manager」。点击后关闭弹窗、跳到新会话，挂上 `expert-manager` 标签，并预填：

```
帮我创建一个 XXX 专家，擅长 XXXXX。我的经验是：[请补充你的行业背景、相关经验]
```

该标签可点 × 移除；进入新会话时自动清除。

#### FR-07 编辑与删除 [原型已实现]

只有「我创建的」专家可编辑 / 删除，内置专家全字段只读。删除前需二次确认，并在确认文案中明确告知**他还在几个专家团里**；确认后从所有自建专家团的成员列表中一并移出，若他是某个团的组长则组长自动顺延为剩余第一位成员。

若被删除的专家正是当前会话的选中对象，选中态一并清空。

### 4.4 专家团配置

#### FR-08 配置弹窗分两个页签 [原型已实现]

- **团队**：名称`必填`、说明、成员（两列，点名字看定义，星标设组长，✕ 移出）、提醒
- **触发词与流程**：常见触发词、运行流程（只读推导结果）

页签标题右侧带小圆点：「团队」有提醒时亮，「触发词与流程」有环节无人可领时亮，用户切在另一页也不会漏掉问题。

内置专家团全字段只读（输入框灰底 + `readOnly`，成员的增删与星标按钮隐藏），底部主按钮是「召唤专家团」，次要按钮「另存为我的专家团」——另存后名称追加「 副本」，来源改为「我创建的」，可自由编辑。

#### FR-09 没有「交付强度」这个旋钮 [已定稿]

早期版本让用户在「快速 / 标准 / 产品级」里选一档来决定走几道门禁。**该设计已废弃**：团里配了谁，本身就已经决定了能走几道门禁，再让用户选一次既冗余又容易和成员矛盾。

用户唯一要做的决定就是**放谁进来**。`deliveryLevel` 仍是后端必填字段，改由前端推导，规则见第 6 节。

#### FR-10 运行流程由成员推导 [原型已实现]

规则一句话：**团里有谁，流程里就有哪一步**。按固定顺序检查，命中则加入该节点：

| 节点 | kind | 出现条件 | 承担人 |
| --- | --- | --- | --- |
| 协调范围与门禁 | `analyze` | 成员 > 1 且团里有 `software-team-lead` | 该组长 |
| 分析需求与验收 | `analyze` | 有 `software-product-manager` | 该 PM |
| 设计方案与实现计划 | `design` | 有 `software-architect` 或 `ux-designer` | 前者优先 |
| 编码准入评审 | `review` | 有 `code-reviewer` 或 `read-only-analyst` | 前者优先 |
| 实现编码任务 | `implement` | **恒定出现** | 实现类专家，无人可领时标红 |
| 安全评审 | `review` | 有 `security-reviewer` | 该评审专家 |
| 质量验证 | `test` | 有 QA，或有非组长成员具备 `verification` | QA 优先 |
| 集成与交付确认 | `integrate` | 成员 > 1 且有人具备 `integration` | 组长 → 架构师 → 其他 |

两个刻意的例外：

- **实现环节永远保留。** 没人能领时显示「⚠ 无人可领」并标红——这是必须暴露给用户的问题，不是可以省掉的步骤。
- **质量验证不回落到组长自己。** 组长验自己协调的活不构成独立验证，因此候选人排除组长本人。

#### FR-11 提醒只留两条硬门禁 [原型已实现]

- 没有成员具备「实现」工作模式 → 实现任务无人可领取
- 没有成员具备「验证」工作模式 → 产出不会被检查，建议加入「软件测试工程师」

这两条是 `expert_team_dispatch` 真会拒绝或空转的情况。其余「建议加 PM / 建议加架构师」之类的软提示一律不做——它们原本是从交付强度派生的，旋钮拿掉后就失去了依据，留着只会在内置专家团上误报。

**还需补一条** [待实现]：当推导出的流程**含 design 节点但团里没有 PM** 时必须提醒。原因见 FR-17。

#### FR-12 触发词编辑 [原型已实现]

每条触发词只有一个输入框（整句自然语言）+ 删除按钮，**不带「说明」字段**。内置数据里已有的说明改为鼠标悬停显示（`title`），不占版面。

内置专家团的触发词以只读卡片展示，点任意一条 = 召唤该团 + 带上这句。

### 4.5 会话中的选择

#### FR-13 选择器在输入框底栏，不是必选 [原型已实现]

位置固定在输入框底部工具栏左侧（`+` 之后），不做成输入框上方的标签。未选中时显示「选择专家」灰字；选中后显示对象名称 + 头像（专家团显示成员叠图）。

下拉分「专家团」「专家」两组，只显示头像 + 名称。**再点一次同一项即取消选择**。

选中态**不跨会话保留**：不写入 localStorage，且从侧栏「新会话」、Logo、首页卡片、⌘N 四个入口进入新会话时一律清空。上一次挑的人不应该悄悄跟到下一个任务里。

#### FR-14 没选就自动匹配，并在会话里说明 [原型已实现]

发送消息时若未选中任何对象，按以下顺序匹配，且必须匹配出结果：

1. **关键词**命中单个专家（工作流 / 表单 / 报表 / 插件 / 接口 / 前端 / 设计 / 测试 / 安全 / 评审 / 架构 / 需求）
2. 命中**两个以上领域**说明一个人扛不住，升级为专家团；苍穹类占多数走「苍穹交付团队」，否则「软件开发团队」
3. 关键词全未命中则看**当前开发模式**（苍穹应用 → 苍穹交付团队，原型探索 → 界面设计专家，通用应用 → 应用速成小队…）
4. 兜底「软件开发团队」

匹配后在第一条用户消息下方插入一条说明，含头像、匹配到谁、为什么、去哪儿换人。底栏 chip 同步更新，用户随时可改。手动选过的绝不覆盖，也不出这条说明。

## 5. 数据模型

原型阶段用 localStorage，键 `lingee.experts.v1`，只存**用户自建的**专家与专家团；内置数据打包在前端。接入后端后整体替换为 `expert-definition.json` / `expert-team.json` 落盘，字段一一对应。

### 原型存储结构

```json
{
  "v": 1,
  "experts": [{
    "id": "my-1788658575228",
    "k": "flow",
    "name": "苍穹工作流开发专家",
    "role": "苍穹流程建模师",
    "desc": "…",
    "tags": ["流程建模", "苍穹工作流"],
    "modes": ["分析", "设计", "实现", "验证"],
    "comp": ["cosmic.workflow · advanced"],
    "cmds": [["帮我设计一个请假审批流程", ""]],
    "steps": ["梳理审批场景与角色", "配置流程节点与条件"],
    "cons": ["流程变更需保留可回滚配置"]
  }],
  "teams": [{
    "id": "team-1788658575228",
    "name": "流程小队",
    "desc": "…",
    "leadId": "software-team-lead",
    "members": ["software-team-lead", "cosmic-workflow"],
    "cmds": [["帮我配一条采购审批流", ""]]
  }]
}
```

`id` 前缀 `my-` / `team-` 加时间戳；`k` 为头像键；`cmds` 为 `[触发词, 说明]`。

### 字段映射

| 原型 | 后端 | 接入时的处理 |
| --- | --- | --- |
| `name` / `role` / `desc` | `displayName` / `profession` / `description` | 后端是 `{ en, zh }` 双语对象，前端只填 `zh`，`en` 留空或同值 |
| `tags`（字符串数组） | `tags`（`LocalizedText[]`） | 同上，逐项包成对象 |
| `cmds[i][0]` | `quickPrompts[i]` | 说明字段（`cmds[i][1]`）后端无对应，仅前端展示用，落盘时丢弃 |
| `modes`（中文） | `allowedWorkModes`（英文枚举） | 需要固定映射：分析→`analysis`、设计→`design`、实现→`implementation`、集成→`integration`、评审→`review`、验证→`verification`、恢复→`recovery` |
| `comp`（`"id · level"` 字符串） | `competencies`（对象数组） | 按 `·` 拆分；level 必须落在四档枚举内，否则拒绝保存 |
| `steps` / `cons` | `workflow.steps` / `constraints` | 直接对应 |
| `k`（头像键） | `avatar`（文件路径） | 前端内置图形需落成 SVG 文件写入专家目录 |
| — | `schemaVersion` `expertType` `source` `revision` `author` `categoryId` `persona` `professionalRoleIds` `knowledge` `outputs` `skills` `tools` `enabled` `contentHash` | 前端不采集，写入时由服务端补默认值。`persona` 缺失会直接影响系统提示词质量（见 GAP-02） |

## 6. 与 expert_team_dispatch 的对接

UI 的产物最终要变成一次 `operation: "start"` 调用。这一节是前后端之间最容易出错的地方，逐条对齐。

#### FR-15 mode 由成员数决定 [待实现]

选中**单个专家**或成员数为 1 的专家团 → `mode: "personal"`；成员 > 1 → `mode: "team"`。用户不需要知道这两个词。

`team` 模式**必须包含 `software-team-lead` 成员**，且 standard/product 或任务数 > 4 时必须有一个无依赖的 `analyze` kickoff 任务派给他。FR-10 推导出的「协调范围与门禁」正是这个 kickoff——所以团里没有组长时，推导结果不含该节点，此时必须降级为 `lightweight`（见下条）或阻止运行。

#### FR-16 deliveryLevel 的推导规则 [待实现]

> **这是拿掉「交付强度」旋钮后必须补上的一环。**
> `deliveryLevel` 在 `expert_team_dispatch` 里**是必填的**（SKILL.md 原文：Always set `deliveryLevel` explicitly）。UI 不再问用户，就必须由前端从推导出的流程里算出来，且算出的值要能通过后端校验。

| 条件（按序命中） | deliveryLevel | 依据 |
| --- | --- | --- |
| 流程含安全评审节点 | `product` | product 强制 review + QA，安全评审只在 product 出现 |
| 流程既无 `review` 也无 `test` 节点 | `lightweight` | lightweight 是唯一允许跳过这两道门禁的档位 |
| team 模式但团里没有组长 | `lightweight` | 无组长则无 kickoff，standard/product 会被后端拒绝 |
| 其余 | `standard` | 默认档 |

推导结果不对用户展示，但**必须写进 Run 的调试信息**，出问题时能对得上。

#### FR-17 PM 与 competency 的强约束 [待实现]

SKILL.md 的硬规则：**`standard` 或 `product` 的 Run 只要含 `design` 任务，就必须恰好有一个 `analyze` 任务派给 `software-product-manager`，且该任务必须设 `competency: "product.requirements"`，每个 design 任务都要直接或间接依赖它。**

对照 FR-10 的推导表：设计节点的出现条件是「有架构师或界面设计专家」，与 PM 无关。因此存在一种会被后端拒绝的组合——**有架构师但没有 PM 的专家团**。内置的「网页交付小队」（界面设计 + 前端 + QA）正是这种情况。

处理方式二选一，**需产品确认**：

- **A（推荐）**：保存时提醒「含设计环节但没有产品经理」，运行时该 Run 降级为 `lightweight`——即 FR-11 里待补的那条提醒
- **B**：设计节点的出现条件改为「有架构师/设计师 *且* 有 PM」，即没有 PM 就不排设计步骤

#### FR-18 review 成员必须 readOnly [待实现]

承担 `review` 任务的成员必须设 `readOnly: true`，且不能评审自己的产出。若组长同时承担评审与最终集成，要用**两个 member 实例、同一个 expertId**：一个只读评审员，一个可写协调者。前端组装 `members[]` 时需要处理这个拆分。

`owns` 字段：实现类成员默认 `["."]`；并行实现时各自声明互不重叠的范围，本期不做并行，恒为 `["."]`。

## 7. 需平台配合的缺口

前端做不完的部分，需要 `packages/opencode` 同步改动，建议与后端同学一起排期。

#### GAP-01 自建专家没有落盘位置 [阻塞创建专家]

`src/expert/registry.ts` 目前只扫描**单个**根目录（`builtin-experts/`，可用 `OPENCODE_EXPERT_ROOT` 覆盖）。Schema 里 `source` 已经允许 `"custom"`，但没有对应的用户级目录，也没有合并扫描逻辑。

需要：新增用户级专家根目录（建议 `~/.lingeebuild/experts/`），registry 改为合并扫描内置 + 用户目录，同名以用户目录优先；并提供写入接口供 UI 调用。**这条不做，FR-06 的手填表单就只是个本地草稿。**

#### GAP-02 persona 缺失会显著拉低自建专家的效果

系统提示词由 `persona.role` + `persona.perspective` + `persona.communicationStyle` + `workflow` + `constraints` 拼成。表单只采集了后两者，`persona` 空缺时提示词会明显偏弱。

建议：走「一句话交给 `expert-manager`」路径时由模型补全 `persona`；手填路径则由服务端按职称 + 简介生成一版默认 persona，允许用户后续在「触发词与工作方式」页签里编辑。

#### GAP-03 专家团缺 orchestrationPolicy [阻塞自建专家团]

`ExpertTeamDefinition` 要求 `orchestrationPolicyRef` 指向一份 SOP（内置团是 `sop/sop.md`）。用户在 UI 里建的团没有这份文件。

建议：提供一份通用默认 SOP，自建团统一引用；本期不开放 SOP 编辑。

#### GAP-04 模式与技能没有绑定 [待评估]

竞品（WorkBuddy）的做法：首页的场景标签在 `scenes.json` 里同时声明 `prompts` 和 `plugins`，用户点一下，插件（技能 + 规则）就写进新会话的 `enabledPlugins`，等于顺手配好了工具箱。

我们目前六个开发模式只携带一个 builder 名字。建议后续让模式 / 专家同时声明「启用哪些技能」——但这超出本期范围，先记录。
