## 1. 背景与目标

空间是 Manage 组织目标、任务、议题、知识和定时任务的单元。空间变大后（多个子系统、多个小组、多条交付线并行），全部任务和资料平铺在一个空间里，出现三个问题：

- 任务列表混在一起，负责人只能靠搜索和筛选找自己那一块。
- 成员、智能体和知识库只有空间一级授权，无法让某个小组只改、只处理自己负责的部分。
- 进度只能按整个空间统计，看不出每条交付线的状态。

目标：在空间下增加**工作区**，作为空间内划分工作范围的层级。工作区可以再分下级工作区，任务归属和成员落在具体工作区上，进度逐级汇总到空间。

不改变的部分：空间仍是立项、预算、负责人和对外协作的单位；不引入空间之上的新层级。注意 manage-build-integration-discussion.md 写的是「本次对接不增加 workspace 概念」，且首期不纳入 workspace 接口；本文要求 Build 任务带上所属工作区并支持筛选，对接接口需新增 `workspaceId` 与路径字段，该对接文档待同步修订，Manage 后端的负责人与排期见第 9 节。

**为什么不只用标签 / 模块字段**：标签只能筛选，不能带成员范围、默认配置和逐级进度汇总。若评审认为一期只需要"按模块筛选"，可降级为空间下的单级「模块」字段（无树、无成员），工作区作为二期；这是第 9 节的评审前置问题。

## 2. 层级与概念

```text
组织 / 租户
└── 空间（立项单位：目标、负责人、模板；仓库与本机目录在 Build 配置）
    ├── 工作区 A（如：后端服务）
    │   ├── 工作区 A1（如：订单模块）
    │   └── 工作区 A2
    ├── 工作区 B（如：移动端）
    └── 未归入工作区的任务与资料（空间根）
```

| 规则 | 建议 |
| --- | --- |
| 层级深度 | 一期限制空间下最多 3 级工作区，超过 3 级不能新建下级，提示改用标签或拆分空间；上限放在一处配置，数据按 `parentId` 存树，后续放宽只改上限，不改数据结构 |
| 是否必须使用 | 可选。没有工作区的空间与现在完全一致；已有任务保留在空间根 |
| 命名 | 同一父级下名称不能重复，不超过 30 字；不同父级下可同名 |
| 归属 | 每个工作区只有一个父级（空间或上级工作区），不支持一个工作区挂到多个父级 |
| 任务归属 | 一个任务只属于一个位置：空间根或某个工作区（任意一级都可以挂任务，不要求挂到叶子） |
| 排序 | 同级工作区可拖动排序，默认按创建时间 |

### 不使用工作区的空间

工作区是可选能力，不是每个空间都要用。研发部门这类多个小组并行的空间会用，一个小团队、一条交付线的项目型空间可以一直不用。

| 场景 | 表现 |
| --- | --- |
| 空间下没有工作区 | 与现在完全一致：详情页头部没有切换箭头，任务列表没有「工作区」列和筛选，新建任务弹窗没有「工作区」字段，概览不分行，Build 里任务标签只显示空间 |
| 入口 | 只有空间负责人、空间管理员在「···」菜单看到「工作区管理」；创建第一个工作区后，上面这些入口才出现。普通成员在此之前看不到任何工作区内容 |
| 首次创建 | 已有任务全部留在空间根，不自动迁移；创建后提示可在任务列表批量「移动到工作区」 |
| 全部删除 | 工作区全部删除后回到「没有工作区」的状态 |
| 空间类型 | 一期只对开发空间（模板「协作开发」）开放，通用空间（管理例会、预算目标、人才布局等）没有「工作区管理」入口，也不显示任何工作区内容；是否扩展到通用空间放二期评审，扩展时数据结构不用改 |

### 名称与 Linky 对齐

「工作区」沿用 Linky（研发协同）的叫法和界面：一棵可展开的树，根是顶层工作区，下面是多级子工作区（Linky 示例：灵基AIOS → 灵基Foundation → 大模型组）。本稿方案：**工作区在空间之内（方案 A）**，与 Linky 只做概念和界面对齐，不做数据互通。界面上的对应关系：

| Linky | 本文 |
| --- | --- |
| 根工作区（如灵基AIOS） | 空间。下拉树第一行就是空间本身，选中代表「全部」，未归入工作区的任务也挂在这一行 |
| 子工作区（灵基Foundation、大模型组等） | 工作区，按层级缩进，可展开、收起 |

不采用「工作区在空间之上」（旧版协作开发的 工作区 > 项目 层级）：那会引入空间之上的新层级，与对接文档的口径冲突。

> **口径风险**：「金蝶研发协同×灵基Build标品融合方案汇报」把「工作区统一还是分开建设」列为待讨论，并写了标品技能「下发到个人 / 团队 / 工作区」。"不互通"只是本稿的产品侧假设，不能当成已定；若融合后统一，「空间 = 根工作区」的映射、成员体系和进度汇总都要重做。需向融合方案对口人确认后再定稿，见第 9 节。

Linky 示例至少有两级子工作区，本文保持空间下最多 3 级。

## 3. 数据关系

| 对象 | 关键字段 | 关系与规则 | 期次 |
| --- | --- | --- | --- |
| 工作区 | `workspaceId`、`spaceId`、`parentId`（空则挂空间）、名称、说明、负责人、排序、状态（正常 / 已归档）、可见性（一期固定「公开」，字段预留） | 属于唯一空间；`parentId` 形成树 | 一期 |
| 工作区成员 | `workspaceId`、`personId`、角色（工作区负责人 / 成员） | 必须是空间成员；**不要求**是上级工作区成员，各工作区成员平行维护 | 一期 |
| 任务 | 新增 `workspaceId`（可空） | 空表示在空间根；移动保持编号不变，并校验目标范围可选仓库与已有任务分支；处理人、审核人必须是该工作区成员 | 一期 |
| 工作区设置 | 工作区指令、默认智能体团队 | 未填写时继承上级，直到空间（继承规则见第 4 节） | 二期 |
| 知识文件 | 新增 `workspaceId`（可空） | 文件夹仍在空间知识库内，工作区视为一级筛选范围 | 二期 |
| 里程碑 | 新增 `workspaceId`（可空） | 工作区里程碑汇总显示在空间概览；需先设计计划页 / 甘特图的层级展示 | 二期 |

仓库列表及各仓库的基准分支归 Build 维护，不在 Manage 的数据里，见附录「多仓库配置、基准分支与本机目录」。议题、定时任务一期仍挂空间，只记录来源工作区，便于筛选。

## 4. 继承与覆盖

继承从上往下逐级取值，下级只填写和上级不同的部分。一期只有「成员」一项生效，其余随二期上线。

| 项目 | 规则 | 期次 |
| --- | --- | --- |
| 成员 | 不继承：每个工作区的成员由其负责人从空间成员中添加，彼此平行，不要求是上级成员。空间负责人、空间管理员对所有工作区可见、可管理 | 一期 |
| 空间指令 / 工作区指令 | 叠加：执行任务时按「空间指令 → 各级工作区指令」顺序拼接，下级在后 | 二期 |
| 智能体团队 | 覆盖：工作区可指定默认团队，新建任务时预选；未指定时用上级的 | 二期 |
| 空间智能体与功能权限 | 继承空间配置；工作区只能收窄（如取消「写入任务产物」），不能放大。是否改为"启用清单 + 私有项"见第 9 节 | 二期评审 |
| 知识库可见范围 | 新增「本工作区」可见范围：仅本工作区成员可见 | 二期 |
| 审核人默认匹配 | 先在任务所在工作区成员中按岗位匹配，找不到再取空间成员 | 一期 |

## 5. 角色与权限

| 能力 | 空间负责人 / 空间管理员 | 工作区负责人 | 工作区成员 | 空间成员（不在该工作区） |
| --- | --- | --- | --- | --- |
| 新建一级工作区 | 可 | 无 | 无 | 无 |
| 新建下级工作区 | 可 | 本工作区下可 | 无 | 无 |
| 改名、移动、归档、删除工作区 | 全部 | 本工作区及下级（移动不能移出本工作区） | 无 | 无 |
| 管理工作区成员与负责人 | 全部 | 本工作区及下级 | 无 | 无 |
| 查看工作区任务 | 全部 | 本工作区及下级 | 本工作区 | 见下方「可见性」 |
| 在工作区新建任务 | 可 | 可 | 可 | 无 |
| 编辑工作区设置 | 可 | 可 | 只读 | 无 |

「工作区成员」只看本工作区；要看下级工作区的任务，需要同时是下级的成员，或由空间级角色、上级负责人授权。

### 可见性

一期所有工作区统一为**公开**：空间成员都能在 Manage 空间详情和统计里看到工作区及其中任务，只有工作区成员能新建和处理。这与 Manage 现在"空间成员看得到全部任务"一致；Build 任务列表仍按现有「只看与我相关」规则，不因工作区改变。

「仅成员」放二期，规则先定下来，避免二期返工：

- 工作区有效可见性取自身及全部上级中最严格的一项：任一祖先为「仅成员」，其下级都按「仅成员」处理。
- 「仅成员」工作区的内容，只有空间负责人、空间管理员、该工作区成员、其上级工作区负责人可见；上级工作区的普通成员不自动可见。
- 非授权者看不到该工作区的任务、知识，列表与概览不显示该行和数量；空间总进度仍包含这些任务，但不分行、不显示名称。
- 公开只解决"只改自己那块"，不解决"只看自己那块"；后者靠「仅成员」。第 1 节第二条的表述已相应收窄。

### 指派与入组

处理人、审核人必须是任务所在工作区的成员，不允许指派后仍无权处理：

- 操作人有该工作区成员管理权（空间负责人、空间管理员、该工作区及上级负责人）：指派不在工作区的人时提示「将同时把某某加入工作区」，确认后只加入该工作区，不连带上级。
- 操作人没有成员管理权：不能指派该人，提示联系工作区负责人（二期提供「申请加入」）。
- 普通成员因此不能通过指派把别人拉进工作区；批量移动任务时，处理人不在目标工作区同样按上面两条处理，并汇总列出需要加入的人，一次确认。

## 6. 入口与页面

### Manage · 空间详情

> 口径已变：Manage 只做空间创建，本小节与下一小节的入口一期改到 Build（协作开发顶部切换器、设置 › 工作区、任务列表的工作区列与筛选）；保留在这里是为了记录原设计的界面要素。

- 以下入口只在空间下已有工作区时显示，没有工作区的空间不变，见第 2 节「不使用工作区的空间」。
- 工作区切换放在空间详情页头部的空间名称处，名称右侧加下拉箭头（位置、形式与 Linky 研发协同顶部的工作区切换一致）。点开是工作区下拉树：顶部搜索框「搜索工作区…」；其下「工作区 N」计数；第一行为空间本身（选中即「全部」）；各级工作区按层级缩进，有下级的带展开 / 收起箭头，当前选中行灰底；不显示任务数；底部「创建工作区」（有权限者可见）。选中后主栏、右栏卡片和底部对话都限定在该范围。地址追加 `&ws=<工作区 ID>`，刷新还原。「加入工作区」（申请加入）放二期。
- 工作区管理放在**开发板块「协作开发 › 设置 › 工作区」**（顶部是旧版样式的空间 / 工作区标题切换器，与 Linky 研发协同的位置一致），不在管理板块；管理板块空间详情的切换器底部「创建工作区」跳转到那里。管理页为树形列表，行内新建下级、改名、排序、移动、归档、删除；右侧为选中工作区的成员、负责人与基本信息：
  - 基本信息：名称（必填，同一父级下不重名）、描述、创建者（只读）；只有空间负责人、空间管理员和该工作区负责人可改，其他人只读。
  - 删除放在页面底部「危险操作」卡片，点「删除工作区」后弹窗要求输入完整的工作区名称才能确认；规则按第 7 节，只能删空的工作区。
- 研发任务列表增加「工作区」列（显示末级名称，悬停显示完整路径），状态筛选旁增加工作区筛选。
- 空间概览按工作区分行显示进度（已完成 / 总任务），点行切换到该工作区。里程碑分行放二期。
- 侧栏「空间」目录树：空间可展开显示一级工作区，点工作区直接进入该范围。
- 二期：配置变更写入空间的「审计日志」。Manage 空间目前没有审计日志（现有 `collab/audit-log.js` 属于协作开发旧版设置），需先由 Manage 提供统一能力，一期原型不做。

- 弹窗增加「工作区」字段（级联选择，只列出本人有新建权限的工作区）。

- 仓库列表及各仓库的基准分支在 Build「设置 › 仓库」维护，本机目录在「设置 › 本机环境」，见附录。

- 工作区负责人变更、工作区归档时通知其成员。

## 7. 关键流程

1. **划分工作区**：空间负责人在「工作区管理」新建一级工作区，填写名称、说明、负责人（从空间成员中选）；负责人自动成为工作区成员。
2. **搭建下级**：工作区负责人在本工作区下新建下级工作区并添加成员。
3. **迁移已有任务**：在研发任务列表多选任务「移动到工作区」；任务的阶段、产物、分支不变，只改归属。处理人、审核人不在目标工作区时按第 5 节「指派与入组」处理。目标范围仍关联原仓库时保留所选仓库；原仓库不在目标列表时，未启动任务需重新选择目标仓库，已启动或已有分支的任务不允许跨仓库移动。
4. **日常协作**：成员在工作区范围内对话建任务；二期起任务预选工作区的智能体团队，执行时带上叠加后的指令。
5. **进度汇总**：工作区进度 = 本级及全部下级任务汇总；空间进度不变，等于全部任务汇总（含空间根）。
6. **归档**：交付线结束后归档工作区：任务、知识保留只读，不能新建任务；进行中的任务需先完成、移走或取消。归档可恢复。级联规则：归档某工作区时，其下级须已归档，否则确认弹窗列出下级并一并归档；恢复下级前须先恢复其上级，否则提示先恢复上级。
7. **删除**：只允许删除没有任务、知识文件和下级工作区的工作区；有内容时提示先移动或改为归档。因此有历史任务的工作区只能归档、不能删除，这是预期（任务需要保留），文案要说明。旧版是级联删除项目和任务，这里不沿用，只借用输入名称确认的弹窗。

## 8. 状态与异常

- 移动工作区不能移到自己或自己的下级下面；移动后超过层级上限（一期 3 级，按整棵子树的深度计算）时不允许。
- 删除空间时连同工作区一起删除（沿用现有二次确认，文案补充工作区数量）。
- 工作区负责人离开空间时，负责人回落到上级负责人（一级工作区回落到空间负责人），并通知空间负责人。
- 成员从工作区移除时，若仍是其中任务的当前处理人，或是尚未完成的后续阶段处理人、审核人，提示先转交；与「有未完成任务的成员不能移除空间」口径一致。
- 成员从空间移除时，同时从所有工作区移除（已受上述未完成任务限制）。
- 工作区成员不要求是上级成员，因此从上级移除某人不影响其在下级的成员身份。

### 2. 多仓库关系与页面设计

#### 工作区与仓库的关系

工作区划分工作范围，仓库存放代码，两者是多对多关系。仓库列表不改变工作区树的组织方式，也不因不同工作区使用同仓库就合并工作区的成员、任务或权限。

例如「费用报销应用」空间下：

| 工作区 | 工作范围 | 关联仓库 |
| --- | --- | --- |
| 报销业务组 | 报销单、审批流程 | expense-web、expense-service |
| 支付业务组 | 付款、支付回调 | expense-service、payment-adapter |

两个业务组的任务分别归属自己的工作区，但都可选择 `expense-service`。同一个人在同一台电脑上默认只初始化一次该仓库，确需跨任务长期隔离的工作范围可配置独立目录；两个任务各用独立任务目录和分支，不能直接共用一个可变的工作目录。

#### 设置 → 仓库

单仓库表单改为仓库列表。每行展示仓库名称、HTTPS 地址、基准分支、默认标记，以及编辑、移除操作；右上角提供「添加仓库」。基准分支属于列表中的具体仓库，不是整个工作区共用一个分支。

- 空间维护自己的仓库列表，可添加多个仓库；同一列表按规范化地址去重，不同空间 / 工作区可重复关联同一仓库。
- 子工作区默认继承上级整份仓库列表及默认仓库，显示「继承自 XXX」，继承状态下只读并跟随上级更新。沿「本工作区 → 上级工作区 → 空间」查找最近的独立列表，替代此前仓库地址、分支逐字段继承的方案。
- 点击「独立配置」以当前生效列表为初始内容，在当前工作区调整仓库、基准分支和默认仓库；之后不再跟随上级更新。提供「恢复继承」，确认后移除当前列表覆盖。独立列表为空表示当前范围没有仓库，不自动回退到上级。
- 每份列表最多一个默认仓库。只有一个仓库时任务自动选中；多个仓库时预选默认项，没有默认项则由用户选择。
- 添加、编辑前校验格式与可访问性，沿用现有 Git 账号规则；关联仓库不代表授予 Git 平台访问权限。谁能维护列表继续按所在范围的 Build 角色校验，仓库授权池规则见第 5 节待决项。
- 移除关联只影响当前范围之后的新选择，不删除远端仓库、本机代码或任务历史。未启动任务的已选仓库失效时，保存 / 启动前提示重新选择；已启动任务保留原快照。

#### 新建 / 编辑任务 → 代码仓库

在「所属工作区」下面增加「代码仓库」，仅代码任务使用；候选项来自当前范围的有效仓库列表。选择仓库后展示其基准分支。

- 只有一个仓库自动选中；多个仓库预选默认项并允许切换。切换空间 / 工作区时，原仓库仍在候选列表中则保留，否则按新范围的默认规则重新选择。
- 没有仓库时提示到 Build「设置 › 仓库」添加；允许先保存任务，启动代码执行前必须完成仓库配置与选择。多个候选但未选择时同样不能启动代码任务。
- 任务开始时保存规范化仓库标识、仓库地址、目标分支快照，之后的阶段、重试、分支展示和代码交付沿用快照；修改默认项、列表或基准分支均不改变进行中任务及历史合并请求。
- 一期一个任务对应一个仓库和独立任务分支，跨仓库需求拆为多个关联任务；不提供单任务同时操作多个仓库。
- 任务详情展示所选仓库与目标分支。已启动或已有任务分支后不能通过编辑、移动改用其他仓库；同仓库移动保持原快照。

#### 设置 → 本机环境

继续按仓库展示，每个规范化仓库一行，显示仓库名称 / 地址、使用它的空间与工作区标签、状态、本机目录、操作。默认复用同一仓库的已有目录，不要求按工作区重复克隆。展开仓库下的工作范围后，可选择复用默认目录、已有的其他目录，或使用独立目录。选择只对当前用户、当前设备生效，不影响团队配置。任务自动使用对应目录，不增加任务选环境步骤。

页面关系：先选择工作范围，再为任务选择仓库，最后按所选仓库复用或准备本机环境。空间 / 工作区仓库列表是团队共享配置，本机目录是个人设备配置。

### 3. 本机目录设计

- **默认绑定按"规范化仓库地址 + 这台电脑 + 这个人"复用，独立目录另有绑定标识**：同一个仓库不管被几个空间或工作区用，本机默认复用目录，允许工作范围关联独立目录。规范化：去掉 `.git` 和末尾斜杠，主机名忽略大小写。
- **默认目录按仓库名**：`<本机根目录>/<仓库名>`，不再用空间名；空间改名不让目录失效，多个空间共用一个仓库时也不会重名。不同主机的同名仓库追加主机或所有者前缀。
- **设置在哪里**：Build「设置 › 本机环境」按仓库列一行——仓库、被哪些空间 / 工作区使用（小标签）、状态、本机目录、操作；首次执行任务时在「准备执行环境」弹窗里就地选目录。管理员配置仓库时不碰本机目录。
- **何时初始化**：不在创建空间时一次性拉取，首次在该仓库下执行任务时再初始化，避免一次拉多个大仓库。
- **任务执行**：按任务选定的仓库（已启动任务取快照）查本机绑定，没有就走准备执行环境；基于本机克隆为任务准备独立任务目录和分支，智能体默认工作目录为该任务目录。不提供代码子目录配置；工作区名称或层级不决定代码目录。多个工作区共用一个仓库时，本机默认复用克隆，也可按工作范围选择长期独立目录；各任务目录相互隔离。
- **规则（沿用 03 文档）**：目录必须在本机根目录内；一个目录只对应一个绑定；允许同仓库存在多个不同目录。未结束任务使用的目录不能更换或解绑，工作范围存在未结束任务时不能切换目录；任务启动后固定绑定，原目录不删。
- **新增规则**：仓库配置改了，旧仓库的绑定保留，新仓库显示「未初始化」，进行中任务不受影响；仓库不再被任何未归档的范围使用且没有进行中任务引用时，目录标记「可清理」；由用户确认移除本机绑定，磁盘代码目录保留；目录被手动删除或移走时状态显示「目录丢失」，点一下重新绑定。
- **名字**：原「工作区目录」改称「本机根目录」，「任务工作区」改称「任务目录」，避免与新工作区混淆（见第 2 节）。

### 4. 仓库不在 Manage 带来的变化

| 位置 | 变化 |
| --- | --- |
| Manage 新建空间（协作开发模板） | 只填名称、目标、负责人，不填 Git 地址和基准分支；创建后引导到 Build 继续配置（成员、仓库、工作区） |
| Manage 空间设置「研发协作设置」 | 去掉仓库与基准分支 |
| Build「新建空间」 | 先调 Manage 新建空间（名称、目标、负责人），成功后再把仓库配置写入 Build 后端；第二步失败要有补偿或重试，不能留下没有仓库的开发空间却没提示 |
| 「按仓库地址查询已有空间」 | Build 按多对多关系返回使用范围；不能因仓库已被其他空间使用就阻止关联或强制复用该空间 |
| 任务接口 | Build 按 `workspaceId` 解析候选仓库列表，记录任务所选仓库；开始时保存仓库与目标分支快照 |
| 删除空间 / 工作区 | Manage 通知 Build 清理对应仓库配置；归档时 Build 标记，不再用于新任务 |
| 权限 | 创建后的成员、角色、工作区负责人都由 Build 维护；空间负责人创建时由 Manage 写入，之后 Build 是权威。谁能改仓库配置由 Build 按自己的角色数据判断 |

### 5. 新增的风险与待决

0. **口径引出的大问题（先答）**：
   - ~~只对开发空间，还是所有空间？~~ **已定：只对开发空间。** 通用空间没有 Build 侧，成员、议题、知识库、定时任务仍在 Manage，与工作区一期只对开发空间开放的范围一致。
   - ~~开发空间在 Manage 的空间详情还留什么？~~ **已定，按下面的建议：**（仅开发空间）议题、知识库、定时任务、里程碑、研发任务列表、成员与权限、邀请，创建后是留在 Manage、迁到 Build，还是隐藏？建议：议题、知识库、定时任务、里程碑这类管理视角的内容仍留在 Manage（它们本来就是 Manage 的能力）；成员与权限、邀请、研发任务列表、仓库、工作区迁到 Build，Manage 详情页只读展示成员和进度汇总并提供「去 Build 配置」入口。
   - 仍待定：邀请迁到 Build 后，待办里的「接受邀请」怎么走；议题批准人原来按空间角色（负责人、管理员）校验，角色改由 Build 维护后怎么校验。
   - **成员和邀请的权威。** 邀请、待办里的「接受邀请」、成员角色在 Manage 现有实现里；改成 Build 维护后，待办入口、角色校验（如议题批准人是空间负责人、管理员）要同步迁移。
   - **任务与进度。** 研发任务数据本来就在 Build，Manage 只读；进度汇总、里程碑「已完成 x/y」在谁那里算。
   - **原型影响。** 我已做的 Manage 侧工作区界面（空间详情切换器、研发任务工作区列与筛选与多选移动、概览分行、侧栏目录树、新建任务字段）需撤掉或迁到 Build；Build 侧已有顶部切换器、设置 › 工作区、任务筛选，可保留。

1. **移动任务不再只改 Manage 一个字段。** 目标列表包含原仓库时保留选择；不包含时，未启动任务需重新选择目标仓库，已启动或已有任务分支的任务不得跨仓库移动；这个判断在 Build，所以 Manage「移动到工作区」需要先问 Build 能否移动，成为跨系统调用。
2. **越权。** 工作区负责人能绑哪些仓库？集成凭据是空间级、由空间管理员配置，建议工作区负责人只能在空间管理员已授权的仓库清单里选，不能填任意地址。
3. **仓库级的集成职责。** git-integration-discussion.md 里的"默认代码集成负责人""启用集成前确认仓库保护规则"改为仓库级，同仓库被多个范围使用时的负责人要定。
4. **两边数据一致。** Build 以 Manage 的 ID 为键，Manage 删除、归档、移动工作区时必须通知 Build，否则出现孤儿配置；原型里两边共用浏览器本地存储，看不出这类问题。
5. **代码子目录已明确取消。** 仓库设置不提供该字段，任务直接使用独立任务目录；以后如有需要另行评审，不预留为当前可配置项。
6. **老数据。** 现有空间目录默认用空间名，改成仓库名后旧绑定是否迁移；原型里可以不迁移，只对新绑定生效。
