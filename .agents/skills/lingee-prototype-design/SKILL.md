# Lingee 原型界面设计

让修改后的界面融入当前原型，并落实到对应页面源码。本 skill 只讲流程；令牌、刻度、组件索引和可做/禁止事项以根目录 `DESIGN.md` 为准，文件归属与验证以 `AGENTS.md` 为准。用户明确指定的设计、截图或参考优先；不因使用本 skill 扩大改动范围。

## 1. 取证

以下路径均相对于项目根目录。

1. 读 `AGENTS.md`、`README.md` 的源码结构与注意事项，检查工作区已有改动。
2. 读 `DESIGN.md`。至少看「现状基线」「色彩」「字体与排版」「间距、圆角与层次」和「组件索引」。
3. 找到目标页面的 HTML、CSS、JS 和弹窗，在「组件索引」中确定本作用域的现行组件。
4. 读 `src/styles/tokens.css` 和目标页实际使用的共享样式，确认 `src/styles/app.css` 的层叠顺序。不要只凭组件预览或旧截图推断实际样式。
5. 有设计稿时：Figma 链接或节点用 Figma 工具读取设计上下文、变量和截图；本地截图在 `design-ref/figma/`（不入库，按页面名查找）。按下文「设计稿对照」处理。新页面和改版页面以 `DESIGN.md`「目标规格」为准。
6. Wiki 存在时按 `AGENTS.md` 的入口查阅；缺失时直接查源码，不编造结论。

依据顺序：用户当前明确要求 → 设计稿 → 目标页当前实现与组件索引 → Design System 预览页示例。

## 2. 设计稿对照

设计稿描述目标样子，源码是现状，二者按以下方式衔接：

- 设计稿颜色、字号、圆角、间距先映射到 `DESIGN.md` 的令牌和刻度；能映射就用令牌，不把设计稿里的字面值直接写进 CSS。
- 映射不上时，判断是设计稿新增的稳定决策还是个别取值：前者在 `tokens.css` 新增令牌并更新 `DESIGN.md`，后者向用户说明差异后再定。
- 设计稿的组件和组件索引里的现行实现不一致时，本次只改目标页，不顺手统一其他作用域，并在交付说明里列出差异。

## 3. 实现

开始前用一两句话说明本次的布局、复用的组件和样式依据；小改动一句即可，不需要额外设计文档或等待确认。

逐条落实，最容易出错的几点：

- 新增和修改的规则只用令牌和 `DESIGN.md` 刻度，不照抄相邻存量代码的字面色值、半像素字号、`650` 字重和字面阴影。
- 需要阅读的文字不用 `--text-soft`；状态同时有文字或图标。
- 按钮、弹窗、菜单、列表页标题区沿用本作用域的现行实现，不新建类名体系。
- 控件处理适用的默认、悬停、`focus-visible`、选中、禁用和加载状态；列表和表单处理空态、无结果、失败和成功反馈。
- 先查父容器的 padding、gap、宽度和滚动责任，再定子区域尺寸；长名称和窄窗口要有截断、换行或局部滚动方案。
- 样式放在页面归属的 CSS，限定作用域；不用裸 `button`、`input` 选择器，不叠加 `!important`，不改归档页面。
- 保留既有 CSS 导入顺序、DOM id 和路由契约；共享样式变更先查调用范围。日常设计修改不更新变更日志。

## 4. 核对

- 对照本次要求检查布局层级、控件行为、适用状态、令牌使用和样式作用域，排除对无关页面的影响。
- 新增了首选组件实现或令牌时，同步更新 `DESIGN.md`。
- 依次运行 `npm run check`（含模块自检与设计规范自检）、`npm run build`、`git diff --check`。
- 默认不启动浏览器；只有任务明确要求时才做浏览器验证。否则交付时说明只做了静态与构建验证，视觉和交互效果未经浏览器验证。
- 说明改动和验证结论；遇到既有错误，说明它与本次修改的关系，不把构建成功当作视觉验收通过。
